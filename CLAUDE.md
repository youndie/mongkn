# CLAUDE.md — mongkn

Kotlin/Native обвязка над MongoDB C-драйвером (`libmongoc`). Чистый Kotlin/Native: `java.*`
и `org.bson.*` здесь недоступны физически.

## С чего начинать сессию

1. [docs/research/research-architecture.md](docs/research/research-architecture.md) — решения
   и их обоснования. Без этого файла задачи выглядят как «сделай очевидное», а очевидное здесь
   трижды неверно:
   - линковаться надо `-lmongoc2`, а не `-lmongoc-1.0`, и заголовки лежат в **версионированном**
     каталоге — поэтому пути разрешаются в Gradle, а не в `.def` (§1.1);
   - `withContext(Dispatchers.Default)` вокруг вызова драйвера — undefined behaviour, а не
     неоптимальность: `mongoc_client_t` не потокобезопасен, а на Kotlin/Native этот диспетчер
     многопоточный (§1.4). `Dispatchers.IO` тоже не выход — на Kotlin/Native он `internal`,
     вопреки собственной документации, поэтому клиент держит свой пул потоков (§1.8);
   - `mongoc_init()` **не** восстанавливает драйвер после `mongoc_cleanup()`: жизненный цикл
     одноразовый на процесс, `MongoClient.close()` намеренно не зовёт `Mongkn.shutdown()` (§1.8);
   - генерации API **больше нет** (решение Р9, M-33): она гарантировала форму, а не поведение,
     и стоила двух JVM-модулей на критическом пути. `MongoCollection` рукописный, его KDoc несёт
     правила снятия формы — в частности, ловушку с двумя одноимёнными перегрузками `updateOne`;
   - официальный JVM-драйвер остался в `:mongkn-difftest` как **эталон**: дифференциальные тесты
     идут тремя фазами вокруг одного mongod, потому что JVM и Native в одном процессе не сводятся.
2. [BACKLOG.md](BACKLOG.md) — что делать. Закрыты вехи M0–M5а. Порядок дальше:
   **M6 (проверки корректности) → M7 (эргономика) → M8 (выпуск)** — номер вехи не приоритет.
   Приоритет сместился на проверки не случайно: почти все утверждения о корректности сегодня
   держатся на ожиданиях автора, а не на эталоне.
3. [docs/coverage.md](docs/coverage.md) — что уже умеет библиотека, а что нет. Отвечает
   на «можно ли этим пользоваться» цифрами, а не ощущением.
4. Документ слоя, к которому относится задача: [docs/features/](docs/features/),
   [docs/api/](docs/api/), [docs/services/](docs/services/).

## На чём это вообще собирается

Хостов ровно два: **macOS/arm64** и **Linux/x86_64**. Всё остальное `build.gradle.kts` отвергает
явной ошибкой, а не молчаливым пропуском задач.

**На Windows напрямую не собрать** — и дело не в упрямстве. Хостовый таргет там был бы `mingwX64`,
которого у нас нет; поиск libmongoc написан под POSIX-раскладку каталогов; а сам C-драйвер
на Windows ставится через vcpkg с другими именами библиотек. Это не «дописать пару путей»,
а отдельная задача сравнимого с вехой размера, и заводить её стоит только если появится
потребитель на Windows.

**Работайте из WSL2.** Внутри WSL хост — обычный Linux x86_64, то есть весь путь ниже
(`libmongoc-dev`, `./gradlew build`, docker compose) работает как есть, без контейнера-обёртки:
машина **уже** Linux, и `ci/linux-build.sh` там не нужен — он существует, чтобы гонять
Linux-сборку **с macOS**.

Две поправки для WSL2 и вообще для x86-хоста:

* в `docker-compose.yml` архитектура образов берётся из `MONGKN_PLATFORM` с умолчанием
  `linux/arm64` (машина автора). На x86 задайте `MONGKN_PLATFORM=linux/amd64` — иначе серверы
  уедут в эмуляцию, и прогон станет вдвое дольше;
* `host.docker.internal` на Linux-докере само по себе не резолвится; но там оно и не нужно —
  тесты идут на хосте и ходят на `127.0.0.1`.

## Сборка

```bash
./gradlew build
```

Предусловие — установленный C-драйвер: `brew install mongo-c-driver` на macOS,
`apt install libmongoc-dev libbson-dev` на Linux. Если он лежит не в `/opt/homebrew`,
`/usr/local` или `/usr`, укажите `-Pmongkn.prefix=<префикс>`.

Собирается **только хостовый таргет**: `cinterop` требует заголовков целевой платформы.
Это решение (Р6), а не недоделка.

**Минимальная поддерживаемая версия libmongoc — 1.26** (решение M-81): это Ubuntu 24.04 LTS
с поддержкой до 2029. Ветка 2.x на Linux из пакетов не ставится нигде, только сборка
из исходников. Проверка границы встроена в CI: Linux-джоба идёт против 1.26, macOS — против 2.x,
то есть каждый прогон проверяет и пол, и потолок.

Чего лишает эта граница (сверено по заголовкам, а не на слух): структурированного логирования,
имени базы в событиях APM succeeded/failed и нового клиентского `mongoc_bulkwrite_*`. Всё это
появилось в 1.30; ничего из этого не блокирует, обходные пути описаны в M-64, M-79 и `bulkWrite`.

Проверить Linux локально **с macOS** (на Linux-хосте это лишнее — там `./gradlew build`
и есть Linux-сборка):

```bash
docker build -t mongkn-ci ci/
```

```bash
./ci/linux-build.sh
```

Контейнер сборки ходит на **те же** серверы, что и хост, — второго комплекта в docker-сети больше
нет. Два следствия, каждое стоило красного прогона:

* внутри контейнера порты серверов **пробрасываются на `127.0.0.1`** (это делает `linux-build.sh`
  через socat). Иначе тесты с `replicaSet=rs0` не находят сервера: одноузловой набор объявляет
  себя как `127.0.0.1:27017`, драйвер после обнаружения топологии идёт по этому адресу и попадает
  в сам контейнер;
* имя `host.docker.internal` обязано быть в SAN серверного сертификата — забытое имя даёт
  «TLS handshake failed», по тексту неотличимое от недоверенного сертификата.

`--platform linux/amd64` обязателен: Kotlin/Native не компилирует на хосте linux-aarch64 (§1.18).

Интеграционным тестам нужны локальные серверы — **без них они падают, а не пропускаются**.
Все четыре контура поднимаются одной командой:

```bash
./ci/dev-servers.sh up
```

Убрать вместе с томами:

```bash
./ci/dev-servers.sh down
```

**Контуров может быть несколько на одной машине** — так и есть с тех пор, как self-hosted раннер
стоит там же, где работают руками. `MONGKN_PORT_OFFSET` сдвигает порты, `MONGKN_PREFIX` — имена
контейнеров и имя проекта compose:

```bash
MONGKN_PORT_OFFSET=100 MONGKN_PREFIX=mongkn-ci ./ci/dev-servers.sh up
```

Адреса для тестов берутся оттуда же, а не считаются заново:

```bash
eval "$(MONGKN_PORT_OFFSET=100 MONGKN_PREFIX=mongkn-ci ./ci/dev-servers.sh env)"
```

Три вещи выяснились прогоном, и каждая ломала разведение по-своему: порт сдвигается **и внутри**
контейнера (иначе реплика-сет объявляет себя портом соседнего контура, и тесты уходят в чужие
серверы); имя проекта compose обязано быть своим (`docker compose down` сносит **проект**,
а не контейнеры по именам — иначе остановка одного контура уносит соседний); и тот же сдвиг
получает инициализация шарда.

Контуров именно четыре, и ни один не сводится к настройке соседа: **27017** — одноузловой replica
set (без него нет change streams и транзакций), **27019** — с `--auth` (включи мы аутентификацию
на первом, креды понадобились бы всем двум сотням тестов), **27020** — с `--tlsMode requireTLS`
(он отвергает любое нешифрованное соединение), **27021** — mongos шардированного кластера
(единственное место, где `readPreference` исполняется кластером, а не расходуется на выбор
сервера у клиента, — M-66). Зачем обёртка поверх `docker compose`: compose описывает контейнеры,
но не умеет `rs.initiate`, заведение пользователей и `addShard` — это шаги после старта,
каждый неочевиден и прокомментирован в скрипте.

За портом 27021 стоит не один процесс, а четыре: конфигурационный реплика-сет, два шарда
и сам mongos. Все они живут в одном контейнере и адресуются по `127.0.0.1` — так раскладка
адресов совпадает с запуском тех же четырёх процессов на машине без docker (macOS-раннер в CI),
и скрипт инициализации получается один, а не два похожих. Шарды драйверу не адресуются никогда,
поэтому наружу опубликован только mongos. Подробности — в шапке `ci/shard/start.sh`.

Память ограничена намеренно: `--wiredTigerCacheSizeGB 0.25` и `mem_limit 512m` на сервер, итого
около 400 МБ на три одиночных сервера плюс ещё 410 МБ на весь шардированный кластер сразу после
старта и около 530 МБ после полного прогона тестов — замерено, а не оценено; лимит у кластера
общий на четыре процесса и равен гигабайту. По умолчанию WiredTiger забрал бы половину ОЗУ машины минус гигабайт.
Данные лежат на диске, а не в tmpfs: tmpfs считается в память контейнера и при этом не даёт
mongod требуемых 500 МБ свободного места — проверено, индексы не строятся.

Сертификаты для TLS **генерируются**, а не хранятся в репозитории: серверный живёт 397 дней
и через год протух бы, сломав сборку без единой правки кода. Ограничение на срок не наше —
на macOS драйвер собран с Secure Transport, а тот применяет политику Apple и отвергает более
долгие серверные сертификаты, показывая `CSSMERR_TP_CERT_SUSPENDED`. Остальные грабли
TLS-контура описаны в шапках `ci/tls/generate.sh` и `ci/tls/start-server.sh`; каждая выглядит
как таймаут соединения.

Ещё две грабли, стоившие по сборке каждая: source set'ы `nativeMain` / `nativeTest` **нельзя**
заводить руками (`by creating`) — их создаёт стандартный шаблон иерархии KMP, а ручной ломает
резолв; и имя теста в обратных кавычках на Kotlin/Native не может содержать запятую.

## Публикация

**Целевая платформа одна — `linuxX64`.** macOS-таргет не публикуется: он нужен для разработки
и для того, чтобы в CI проверялась ветка mongo-c-driver **2.x** (в Ubuntu только 1.x). Не удаляйте
macOS-джобу как «ненужный таргет» — вместе с ней исчезнет половина проверки решения Р1.

`ru.workinprogress.mongkn`, приватный Reposilite. Публикует workflow `publish` — вручную,
`gh workflow run publish.yml`. Версия по конвенции соседних проектов: `0.1.<номер прогона>`
либо заданная параметром.

Раннер — **в WSL** (`self-hosted, Linux, X64, wsl`): там нативный Linux x86_64 с libmongoc 1.26,
то есть ровно публикуемая платформа. Собирать на macOS-раннере нельзя: там доступна только задача
`publishMacosArm64…`, и наивная публикация выложит `macosArm64` под координатами mongkn —
потребитель получит «No matching variant» вместо библиотеки.

Креды берутся из секретов организации `REPOSILITE_USER` / `REPOSILITE_SECRET`; в репозитории
их нет. Локально те же имена читаются из `~/.zshrc`, то есть видны **только интерактивной**
оболочке.

Последний шаг workflow проверяет **артефакт**, а не зелёный прогон: скачивает `.module`
и падает, если в нём нет варианта `linux_x64`.

**Опции линковки обязаны быть в klib, а не в `binaries.all`.** Первая публикация была зелёной
и при этом непригодной: у потребителя линковка падала сотней `undefined symbol` из libbson.
Опции из `binaries.all` действуют только на бинарники самого проекта; теперь `.def` генерируется
с разрешёнными именами и путями (`mongkn-core/build.gradle.kts`). Проверять это надо сборкой
настоящего потребителя — зелёная публикация об этом не скажет.

Перед отправкой на сервер стоит прогнать `publishToMavenLocal` и посмотреть координаты:
`group` подпроектами не наследуется, и артефакты однажды уже уехали не туда.

## Переносимое знание

Практика обвязки C-библиотеки из Kotlin/Native, добытая на этом проекте, вынесена в скилл
`kotlin-native-cinterop` (`~/.claude/skills/`): `.def` и поиск библиотеки, владение памятью,
блокирующие вызовы и отменяемость, курсоры во `Flow`, сборка под Linux, сверка с эталоном.
Если беретесь за похожую обвязку — начните с него, а не с этого репозитория.

## Форматирование

ktlint в гейте: плагин вешает `ktlintCheck` на `check`, поэтому обычный `./gradlew build`
его прогоняет, и отдельной строки в CI не нужно. Починить формат:

```bash
./gradlew ktlintFormat
```

Версия форматтера задана явно — `ktlint = "1.8.0"` в каталоге; плагин лишь запускает CLI.
Стиль и длина строки — в `.editorconfig` (`ktlint_official`, 120 символов).

Две вещи ktlint не чинит сам и придётся править руками: **KDoc перед выражением** (не перед
объявлением) — в `.kts` это частый случай, меняйте на `/* */`; и **два KDoc подряд** —
обычно след неаккуратной правки.

## Замер производительности

Числа и методика — [docs/performance.md](docs/performance.md). Запуск:

```bash
./gradlew :mongkn-core:runBenchmarkReleaseExecutableMacosArm64
```

Бенчмарк — **отдельный release-исполняемый файл, а не тест**: тестовые бинарники Kotlin/Native
собираются в DEBUG, и снятые на них числа описывают отладочную сборку. Он входит в `assemble`,
то есть добавляет линковку к сборке при изменении тестовых исходников. Это осознанная цена:
невкомпилированный бенчмарк тихо сгниёт на первом же рефакторинге внутренних API — так уже
случилось бы при появлении `Target` в M14.

## Правило про документацию

> **`main` описывает то, что есть.**

Меняешь поведение, описанное в документе, — правь документ тем же PR. Проверяй утверждение
по источнику (заголовок C, прогон, артефакт в Maven Central), а не по соседнему документу.
В ресёрче прогоны, чтение заголовков и гипотезы разделены намеренно — не смешивай их при правке.
